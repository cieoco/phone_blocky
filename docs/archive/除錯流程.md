以下這份流程圖與說明，目的是為了在**重新整理程式架構**（採用兩階段轉譯、拆分程式檔案、並引入更系統化的開發方式）之後，幫你在「**新增功能**」與「**除錯**」時，有一套**清晰的步驟**可遵循。整個流程包括：

1. 在前端 **（Blockly/JS）** 新增或修改程式/積木。  
2. 在 Arduino/ESP32 **（C++）** 端配合實作或修改指令解析。  
3. 做 **本地測試 / 模擬** 與 **硬體測試 / 除錯**。  

以下是大致流程建議，供你在專案中導入並做調整。

# 一、整體開發流程概觀

```mermaid
flowchart TB
    A[1. 創建或切換到 新功能分支] --> B[2. 新增或修改 前端積木、IR、轉譯器程式]
    B --> C[3. 在前端瀏覽器環境測試]
    C --> D[4. 若需要: 調整 Arduino/ESP32 端對應指令解析]
    D --> E[5. 透過 WebSocket/串流測試前後端互動]
    E --> F[6. 撰寫/更新 測試案例(若有自動化)]
    F --> G[7. 進行 最終硬體測試 與除錯]
    G --> H[8. 確認功能OK -> 發起合併 (merge) 回主分支]
    H --> I[9. 打Tag/Release, 或繼續下一個功能]
```

### 解說
1. **創建/切換分支**：  
   - 使用 Git 或其他版本控制工具，先開一個新的功能分支(Feature Branch) 或切換到對應分支，避免與現有穩定主分支衝突。
2. **在前端新增/修改程式**：  
   - 包括：  
     - (a) **Blockly 積木定義**  
     - (b) **IR Node**（若有需要新 IR 類型）  
     - (c) **翻譯器 (Translator)**  
     - (d) **parseBlocks** (或 parseStatementInput) 裡新增對新積木的處理  
     - (e) 其他 UI/UX 調整  
3. **前端瀏覽器環境測試**：  
   - 先不碰實體硬體，只看「積木能不能正常顯示、組裝，產生的 JSON 是否正確」；也可以在瀏覽器主控台 (Console) 查看 Log。  
4. **(視需要) Arduino/ESP32 端更新**：  
   - 有些功能若後端 `CommandProcessor` 原本不支援，就要新增 `executeCommand` 的對應分支，或新增更多函式庫/硬體驅動等。  
   - 如果是單純前端就能處理的邏輯（例如把結果算好再印），就可能不需要改 C++ 端。  
5. **WebSocket 互動測試**：  
   - 用 ESP32 + 瀏覽器連線，看指令能否順利送出、後端能否正確執行、回傳。  
   - 檢查瀏覽器 Console 與 ESP32 序列埠 (Serial Monitor) 的輸出。  
6. **撰寫/更新 測試案例**：  
   - 有條件的話，可寫一些單元測試 (JavaScript 端) 或 C++ 端的測試來確保功能無誤。  
7. **最終硬體測試 與除錯**：  
   - 實際接線、測試硬體周邊（馬達、感測器、LED…）。  
   - 假如發現問題，就回到前面步驟修正；循環直到功能正常。  
8. **功能 OK -> Merge 回主分支**：  
   - 確認在分支裡開發完畢後，發起 Pull Request / Merge Request，合併回主線，維持乾淨的主分支。  
9. **打 Tag / Release** 或繼續下一輪**：

# 除錯實例記錄

## 2025/09/26 - 桌面右鍵光標跳動問題解決

### 問題描述
在 Blockly 工作區中按右鍵時，滑鼠光標會跳動到其他位置，影響用戶操作體驗。

### 問題症狀
- 在 blockly.html 頁面中右鍵點擊時，光標會從點擊位置跳動到其他位置
- 其他功能（拖拽積木、左鍵點擊等）正常運作
- 問題僅發生在桌面環境，手機端無異常

### 除錯過程
1. **系統性測試方法**：創建多個測試文件，逐步排除可能的原因
2. **測試文件清單**：
   - test_blockly.html - 基本 Blockly 載入測試
   - test_minimal.html - 最小化配置測試  
   - test_without_app.html - 移除 app.js 測試
   - test_only_appblock.html - 僅載入 appBlock.js 測試
   - test_complete_basic.html - 完整基本功能測試
   - 以及其他 10+ 個測試文件

3. **關鍵發現**：
   - 問題不在於 JavaScript 文件載入順序
   - 問題不在於 HTML DOM 結構
   - 問題不在於 CSS 樣式設定
   - **根本原因**：blockly.html 中的內聯腳本修改了 Blockly.Workspace.prototype

### 根本原因
```javascript
// 問題代碼：blockly.html 中的內聯腳本
Blockly.Workspace.prototype.getAllVariables = function() {
    // 這個原型修改導致了事件處理異常
};
```

### 解決方案
1. **移除問題腳本**：註解掉 blockly.html 中修改 Blockly 原型的內聯腳本
2. **保持功能完整**：所有核心功能（積木拖拽、程式生成、WebSocket 通信）均正常運作
3. **驗證解決**：用戶確認「OK了喔」，右鍵光標跳動問題完全解決

### 技術要點
- **不要修改第三方函式庫的原型**：修改 Blockly 等第三方函式庫的 prototype 可能導致不可預期的副作用
- **事件處理敏感性**：DOM 事件處理機制對原型修改極為敏感
- **系統性測試的重要性**：通過建立多個測試環境，能夠有效隔離問題根源

### 受影響文件
- `data/blockly.html` - 移除了問題的內聯腳本
- `data/appIr.js` - 修復了語法錯誤（缺少分號）

### 預防措施
1. 避免直接修改第三方函式庫的原型
2. 如需擴展功能，使用組合模式而非繼承/原型修改
3. 建立系統性測試流程，在出現複雜問題時能快速定位根因

### 結論
這次除錯展示了系統性測試方法的重要性。通過建立多個隔離的測試環境，成功識別出問題的根本原因不在於常見的 JavaScript 載入或 DOM 操作問題，而是在於對第三方函式庫原型的不當修改。這個經驗提醒我們在處理複雜的前端問題時，要特別注意第三方函式庫的使用方式。

   - 有正式版需求時，可以在主分支打 Tag 或 Release；若還有新功能需求，就再開下一個分支。

# 二、在前端「新增函式/程式」的步驟

例如你要新增一個 **motor_control** 積木與指令(只是示例)：

1. **建立/編輯對應的 Blockly Block**  
   - 在 `block_definitions.js`（或你的單檔 `app.js`）中，新增一個積木定義：
     ```js
     Blockly.Blocks['motor_control'] = {
       init: function() {
         this.appendDummyInput()
             .appendField("馬達控制,馬達編號:")
             .appendField(new Blockly.FieldNumber(1, 1, 4), "MOTOR")
             .appendField("方向:")
             .appendField(new Blockly.FieldDropdown([["前進","F"],["後退","B"],["停止","S"]]), "DIRECTION")
             .appendField("速度:")
             .appendField(new Blockly.FieldNumber(0, 0, 255), "SPEED");
         this.setPreviousStatement(true, null);
         this.setNextStatement(true, null);
         this.setColour(180);
       }
     };
     ```
2. **新增對應 IR Node (可選)**  
   - 若想讓程式維持兩階段轉譯，就做個 `MotorControlNode`。例如：
     ```js
     class MotorControlNode extends BaseNode {
       constructor(motor, direction, speed) {
         super();
         this.motor = motor;
         this.direction = direction;
         this.speed = speed;
       }
       toJson() {
         return {
           command: "motor_control",
           motor: this.motor,
           direction: this.direction,
           speed: this.speed
         };
       }
     }
     ```
3. **新增一個翻譯器 (Translator)**  
   - 例如 `translateMotorControl(block)`，把積木的資料轉進 `MotorControlNode`：
     ```js
     function translateMotorControl(block) {
       const motor = parseInt(block.getFieldValue('MOTOR'), 10);
       const direction = block.getFieldValue('DIRECTION');
       const speed = parseInt(block.getFieldValue('SPEED'), 10);
       return new MotorControlNode(motor, direction, speed);
     }
     ```
4. **在 parseBlocks (或 getTranslator) 中註冊**  
   ```js
   function getTranslator(blockType) {
     switch(blockType) {
       // ...其他
       case "motor_control": 
         return translateMotorControl;
       default:
         return null;
     }
   }
   ```
5. **測試：在瀏覽器中拖拉積木**  
   - 看看能否正確生成 IR → JSON  
   - 打開瀏覽器開發者工具 (Console)，看看印出的 JSON 是否如預期：  
     ```json
     {
       "mode": "PROG",
       "setup": [...],
       "loop": [
         { "command": "motor_control", "motor": 1, "direction": "F", "speed": 100 }
       ]
     }
     ```
6. **若後端 Arduino 也需要新指令解析**：  
   - 在 `CommandProcessor` 裡，為 `"motor_control"` 新增對應的 `else if` 區塊，確保能執行對應函式 `motorCtrl.controlMotor(...)`。  
7. **前後端測試**：  
   - 結合 WebSocket，送出指令給 ESP32，ESP32 打印或動作都正確，再驗收這個功能。

# 三、除錯（Debug）建議流程

假設功能沒跑起來，或結果怪怪的，該怎麼一步步 Debug？

1. **檢查前端積木連結是否正確**  
   - 先確認你在 Blockly 上的積木有沒有接錯、參數有沒有填對（尤其引腳值、速度等）。  
2. **檢查「翻譯」結果**  
   - 在開發者工具 (Console) 看看產生的 JSON 內容是否符合預期？  
   - 例如你想要馬達速度 255，卻看到 JSON 寫 0，就代表翻譯函式出錯。  
3. **檢查 WebSocket 傳輸**  
   - 看 Console 是否有 `ws.send(...)` 成功？  
   - 看 ESP32 端序列埠 (Serial Monitor) 是否收到該指令？  
4. **檢查 Arduino 端 `CommandProcessor`**  
   - 有沒有對應的 `else if (strcmp(command, "motor_control") == 0)` ？  
   - 數值是否正確解析？  
   - 在指令中，有沒有 `Serial.println(...)` 說明馬達實際設了什麼參數？  
5. **檢查硬體連線**  
   - 如果在軟體層面都沒問題，接著才檢查馬達電路、電源、引腳連線等。  
6. **重複測試**  
   - 在硬體上重複測試；若仍有問題，就回到 (2) or (4) 修正程式，直到 OK。  

> 建議你**盡量在程式每個階段多加 `Serial.print(...)` 或 Console.log(...)** 之類，讓整個流程更透明。就像「在途中設路標」，出問題時會比較好找。

## 2025年9月26日 - Blockly右鍵選單游標跳動問題 ✅ 已解決

### 問題描述
在桌面版環境中，使用Blockly工作區時發現右鍵點擊會造成游標跳動到其他區域，影響使用體驗。具體表現為：

- 問題僅在桌面環境出現，網頁版正常
- 影響正常的右鍵選單使用

### 除錯過程
採用**系統性隔離測試法**，透過建立多個測試檔案逐步排除問題源頭：

1. **基礎環境測試** - 確認問題存在於blockly.html
2. **JavaScript檔案隔離** - 測試不同JS檔案組合的影響
3. **HTML結構分析** - 檢查DOM元素對事件處理的影響
4. **逐步回退測試** - 從最簡版本開始，逐步添加功能

#### 測試檔案清單
建立了15+個測試檔案進行系統性測試：
- `test_minimal.html` - 最基本Blockly環境
- `test_without_app.html` - 移除應用程式相關JS
- `test_no_buttons.html` - 移除按鈕相關程式碼
- `test_simple_note.html` - 簡化版本測試
- 等等...

### 根本原因 🎯
**問題核心**：blockly.html中的內聯腳本修改了Blockly原型

具體來說，以下程式碼造成了事件處理異常：
```javascript
<script>
  // 修改 Blockly API 以兼容較舊版本
  if (typeof Blockly.Workspace.prototype.getAllVariables === 'undefined') {
    Blockly.Workspace.prototype.getAllVariables = function() {
      return this.variableMap ? this.variableMap.getAllVariables() : [];
    };
  }
</script>
```

**技術分析**：
- 修改第三方函式庫的原型方法會干擾其內部事件處理機制
- Blockly的右鍵選單系統依賴精確的事件座標計算
- 原型修改可能導致事件冒泡或座標計算出現異常

### 解決方案 ✨
1. **移除問題腳本**：完全移除上述內聯腳本
2. **保持原始API**：讓Blockly使用其原生的事件處理機制
3. **功能驗證**：確認所有核心功能仍正常運作

### 實施步驟
1. 註解掉blockly.html中的API兼容性腳本
2. 測試右鍵選單功能 - ✅ 正常
3. 驗證所有積木功能 - ✅ 正常
4. 確認程式碼生成 - ✅ 正常

- ✅ 右鍵選單游標不再跳動
- ✅ 所有Blockly核心功能正常
- ✅ 積木拖拽功能正常
- ✅ 程式碼生成功能正常
- ✅ 用戶確認：「OK了喔」

### 重要學習要點 📚
1. **第三方函式庫修改風險**
   - 修改原型可能造成意外副作用
   - 特別是事件處理相關的功能
   - 應優先使用官方API或配置選項

2. **系統性除錯方法**
   - 隔離測試能有效定位問題
   - 從最簡環境開始逐步增加複雜度

   - 優先使用官方支援的方法

# 結論

1. **整個流程**可用 Git Workflow + 兩階段轉譯概念輔助。  
2. **新增程式 / 新功能**：主要在前端新增對應的積木、IR、翻譯器；若後端需要支援，就增添對應指令解析。  
3. **除錯**：分段檢查「積木設定 → 翻譯 → WebSocket → Arduino 端 → 硬體」各階段。  
4. **測試完成**後就可 Merge 回主分支、發佈或繼續開發。  
5. **實際案例學習**：如本次右鍵游標跳動問題，透過系統性隔離測試法成功定位並解決第三方函式庫原型修改造成的事件處理異常。

如此一來，就能有條有理地逐步改進、擴充功能，也更容易追蹤和解決問題。希望能對你有所幫助，祝開發順利！
