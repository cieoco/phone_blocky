# phone_blocky 線上課程

> 一套可自學的錄播短影課程，帶完全沒有經驗的人走完一輪電控。

---

## 這門課的立場

電控入門的挫折，絕大多數不是來自電控。

驅動裝不起來、COM port 找不到、燒錄失敗、少一個分號、腳位對照、0–255 還是 ±255、
改一行等三十秒編譯、看不到內部狀態只能猜——這些佔掉初學者八成的挫折，
但**沒有一個教會他們任何關於電控的事**。

phone_blocky 把這些整批拿掉：韌體只燒一次、程式用手機拖積木、單位直接是度和 RPM、
接線是固定的、狀態即時看得見。

剩下的挫折——接線要接對、電源要夠、開迴路不準、有負載會掉——**才是真正值得卡的地方**。

> 這門課不是把電控變簡單，是把「不屬於電控的困難」拿掉，
> 讓學習者的挫折預算全部花在真正該花的地方。

## 課程骨架

**動 → 準 → 穩 → 判 → 交**

| 季 | 主題 | 學生體驗到的問題 | 學到的真概念 |
|---|---|---|---|
| S0 | **上車** | 我要怎麼開始 | — |
| S1 | **動** | 它轉了，但快慢我說了不算 | 開迴路、PWM 不等於速度 |
| S2 | **準** | 我要它停在 90°，它過頭了 | 位置回授、編碼器 |
| S3 | **穩** | 我用手推它，它回來了；加負載就掉 | 誤差、增益、死區、擾動 |
| S4 | **判** | 它自己看到障礙就停 | 感測、條件、狀態 |
| S5 | **交** | 我量到的數字別人能直接用 | 參數化、單位、規格移交 |

## 兩個核心指標

| 指標 | 定義 | 在哪達成 |
|---|---|---|
| **time-to-first-life** | 從打開課程，到親眼看見馬達會動、編碼器數字會跳 | 自檢頁（E05） |
| **time-to-first-control** | 到馬達**照學員的意思**轉動 | 搖桿頁（E06） |

第一個證明「東西是活的、我沒接壞」，第二個證明「我能指揮它」。
這兩個數字決定學員會不會留到第二集，所有課程設計以此為準繩。

## 每支短片的固定格式

```
1. 回扣（10 秒）  「上一集你應該已經看到 X」
2. 一個問題       這集要解決什麼（只有一個）
3. 動手           實際操作
4. 成功訊號       「你現在應該看到 Y」← 不可省略
5. 卡住了？       指向診斷表對應條目
6. 下一集的鉤子   留一個沒解決的疑問
```

**第 4 與第 5 項是錄播格式的生死線。** 沒有現場助教，學員必須能自我驗收、自我診斷。

成功訊號必須是可觀察的具體事實：

- ✗ 「接好線之後應該就可以了」
- ✓ 「手機 WiFi 清單裡會出現 `ESP32-` 開頭的熱點」
- ✓ 「M3 那一列會從『等待中』變成綠色的『通過』」

## 教學設計上的兩個關鍵決策

### 1. 自檢頁不只是驗收，它是第一堂課

[`hardware_test.html`](../../data/hardware_test.html) 每一項測試都會先說「請注意觀察 X」，
跑完自動序列後給出量化證據（編碼器計數範圍與總變化量、距離範圍、測量次數），
再附上明確判準：「正常情況：馬達轉動時計數應明顯變化」，**最後由學員自己回答是否正常**。

它是 human-in-the-loop 的——不是機器判通過，是逼學員真的去看。

**直接後果**：學員在 E05 驗收硬體時，就已經親眼看到「馬達轉 → 有個數字跟著變」。
那就是回授的概念，只是還沒被命名。

所以 **E05 只叫學員留意、不解釋**；到 E20 講編碼器時，開場是
「還記得自檢時那個跳動的數字嗎」——不是引入新概念，是替他早就看過的現象取名字。

### 2. 診斷表以自檢失敗項目為索引

[卡住了怎麼辦](../卡住了怎麼辦.md) 不是自由發想的症狀清單，而是照著自檢頁的 9 個項目編排。
工具已經幫學員把問題定位到某一項了，診斷表只要接手那一項。

## 給想自己開課的老師

這套教材可以直接拿去用、改，唯一的請求是保留兩件事：

1. **成功訊號不要省。** 沒有它，自學者無法判斷自己該不該往下走。
2. **自檢先於程式。** 不要跳過 E06 直接教積木——硬體沒驗過就寫程式，
   之後每一個問題都會變成三個可能（程式？接線？機構？），而學生沒有能力做二分法。
