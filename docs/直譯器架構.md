# 直譯器架構：為什麼積木程式不用編譯就能執行

> 說明 phone_blocky 的 Blockly 積木程式如何「即傳即跑」。對應韌體：
> [src/CommandProcessor.h](../src/CommandProcessor.h)、[src/main.cpp](../src/main.cpp)；前端：[data/app.js](../data/app.js)。

---

## 一句話

韌體（`CommandProcessor`）**早就燒錄好了**，它是一個常駐的「JSON 指令直譯器（interpreter）」。
積木程式從頭到尾只是被翻譯成**資料（JSON）**，透過 WebSocket 丟給這個直譯器；韌體讀資料、
查表、呼叫早已編譯好的 C++ 函式。**過程中沒有任何 C/C++ 原始碼被產生或編譯。**

這是「**直譯器**」架構，不是「**編譯器**」架構。

---

## 對照：傳統 Arduino 積木 vs phone_blocky

| | 傳統 Arduino 積木（mBlock / ArduBlockly…） | phone_blocky |
|---|---|---|
| 積木輸出 | **C++ 原始碼字串** | **JSON 資料** |
| 上板方式 | 編譯成 `.bin` → 重新燒錄 → 重開機 | WebSocket 傳一段 JSON |
| 改程式 | 每次都要重編譯＋燒錄（數十秒） | 即時生效（毫秒） |
| 韌體角色 | 每支程式 = 一份新韌體 | 韌體固定不變，只換資料 |

## 執行流程

### 前端（瀏覽器，4 步）— 全是「資料轉換」，產物是 JSON

```
拖積木 → parseWorkspaceToIR()   [appJson.js]
       → node.toJson()          [appIr.js]   每個積木 = 一條 JSON 指令
runBlocklyCode()                [app.js]
       → { mode:'PROG', setup:[...], loop:[...] }
       → ws.send(JSON.stringify(payload))    ← 只是送字串，沒有編譯
```

### 韌體（ESP32，已燒錄的直譯器）

```
收到 JSON → processCommands()       判斷 mode:"PROG"
          → parseProgCommands()     把 JSON 解析成資料結構
                                    std::vector<BlocklyCommand>（填欄位的 struct，不是程式碼）
主迴圈 jsonTask（每 10ms）→ executeLoopCommands()
                          → executeSingleCommand()
                            switch(cmd.type) 查表 → 跳到早已編譯好的動作
                            （setMotorDuty / controlServo / startMotorPositionMove …）
```

**關鍵在這個 `switch-case` 直譯器**：`executeSingleCommand` 裡每個 `case CMD_*` 都是事先寫死、
編譯進韌體的 C++。積木程式只是在決定「選哪個 case、帶什麼參數」。

| 環節 | 位置 |
|------|------|
| 前端送出 PROG JSON | [data/app.js `runBlocklyCode`](../data/app.js) |
| 指令入口 / mode 分流 | [`CommandProcessor::processCommands`](../src/CommandProcessor.h) |
| JSON → 資料結構（staging）| [`stageProgCommands`](../src/CommandProcessor.h) → `std::vector<BlocklyCommand>` |
| 指令資料結構定義 | [`struct BlocklyCommand`](../src/CommandProcessor.h) |
| 安全點套用新程式 | [`applyPendingProgramIfAny`](../src/CommandProcessor.h)（jsonTask 內 swap） |
| 每 10ms 跑一條 loop | [`jsonTask`](../src/main.cpp) → [`executeLoopCommands`](../src/CommandProcessor.h) |
| 查表派發（直譯器核心）| [`executeSingleCommand` 的 `switch(cmd.type)`](../src/CommandProcessor.h) |

> **PROG 採 staging-swap 跨任務交接**：WebSocket / 序列指令在 AsyncTCP（core 0）任務解析，
> 而 loop 執行與角度控制在 `jsonTask`（core 1）。為避免「執行中的指令向量被另一核心
> `clear`/重配置 → 持有的參考懸空（use-after-free）」，新程式先解析進 staging 向量，
> 再由 `jsonTask` 在迴圈安全點以 `swap` 套用。如此 active 向量自始至終只被單一任務動到，
> 鎖也只在極短的 swap 期間持有（絕不跨越 `delay`）。

## 為什麼能「即時」也能「斷電自動跑」

- **即時**：換的是資料不是韌體，傳完馬上由常駐直譯器執行。
- **存檔 / autorun**：JSON 存到 LittleFS（`/program.json`，見 [src/ProgramStore.h](../src/ProgramStore.h)），
  開機時讀回同一份 JSON 餵給同一個直譯器即可，仍然不需要編譯。
  詳見 [prog_json_schema.md](prog_json_schema.md) 的 autorun 一節。

---

## 代價（直譯器的取捨）

- 只能用韌體**預先實作好的指令集**（`pwm` / `speed` / `move_to` / `move_by` / `servo` / `if` …）。
  指令清單見 [prog_json_schema.md](prog_json_schema.md)。
- 要新增「一種全新動作」時，**才需要**改韌體 `executeSingleCommand` 並重新編譯燒錄一次；
  之後該動作就永久成為積木可組合的元件。
- 效能與彈性比原生編譯碼低（多了 JSON 解析與 switch 派發），
  但對「桌上驗證機械行為」這個用途綽綽有餘。

---

## 小結

> 編譯這件事在「**做韌體**」時就一次做完了；
> 積木程式是在已編譯好的直譯器上「**組裝資料**」，所以不用再編譯。
